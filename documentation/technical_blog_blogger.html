ACOUSTICX INTELLIGENCE · NEXTWAVE AI AND ML

How we assembled an acoustic-event dataset, compared two independent model paths, and designed a reviewable alert workflow for uncertain sound detections.

Project team: Saeed Ahmed · Manahil Khan · Muhammad Kaif · Sahil Karim Lakahni
29 September 2026 · Technical blog for the SonicSentinel AI SRS

This article describes the repository and its recorded evaluations. SonicSentinel is a competition prototype for controlled testing. A classifier result is evidence for human inspection, not proof that an emergency has occurred or that a scene is safe.

The business problem and its background

Industrial plants, building entrances, and public spaces can produce more sound than one person can monitor continuously. A machine fault may be hidden beneath ordinary operation. A brief glass break, scream, or call for help can be missed in a long recording. At the other extreme, a false gunshot or fault alarm can waste attention and create an inappropriate response. SonicSentinel AI was built around that tension: detection must be quick enough to be useful, while the underlying audio and the uncertainty must remain available to a person who will decide what happens next.

The software requirements specification names ten mandatory categories: Machinery Fault, Glass Breaking, Alarm or Siren, Vehicle Horn, Animal Sound, Gunshot, Panic Scream, Aggression, Person Asking for Help, and Background Noise. The project also added Normal Machinery. That extra class matters because a machine making normal operating noise should not be labeled faulty merely because it was recorded in a factory. The categories mix operational and safety contexts, so one global alert threshold would be a poor fit. A horn and a possible gunshot deserve different routing, repetition checks, and human attention.

The requirements call for both a Python classifier and a separately trained Google Teachable Machine, or GTM, classifier. They also ask for audio-quality checks, model comparison, waveforms, spectrograms, configurable critical-event rules, and live microphone monitoring. The implementation keeps those pieces visible in a Django application. We treat its results as a structured triage aid: it helps operators find, inspect, and document recordings, but does not replace a trained responder or validate a real emergency on its own.

Proposed solution and architecture

A user can upload one recording, an authorized operator can upload a batch, or a user can start a browser-microphone session. The browser runs the exported GTM TensorFlow.js model locally. It sends the audio and GTM scores to Django, where the server validates the file, assesses quality, preprocesses samples, and runs the selected Python model. The models do not use each other's predictions as input. The decision layer compares their labels and confidence values, applies configurable rules, and creates an event, review item, or alert. SQLite stores event metadata and actions; the original audio is kept outside the public static directory.

The code is separated by responsibility: sonic.dataset builds source metadata and splits; sonic.quality grades recordings; sonic.preprocessing standardizes waveforms; sonic.features extracts values for classical and neural models; sonic.models trains and evaluates candidates; and sonic.web handles users, uploads, monitoring, reviews, alerts, analytics, and exports. A JSON class registry keeps names consistent across training and the web app. The project report has data-flow and sequence diagrams linked to these modules.

The application uses uv for environment management. pyproject.toml declares dependencies, uv.lock pins them, and .python-version selects Python 3.11.9. A fresh checkout can run uv sync --locked, migrate the local database, and start Django through uv run. The frozen YAMNet backbone is downloaded from TensorFlow Hub on first Python inference and cached under the configured data directory. The README documents the exact installation commands and this first-run network requirement.

Dataset collection, ethical sourcing, and difficult cases

The recorded dataset has 3,347 unique original clips, with 2,343 training, 502 validation, and 502 test recordings. The ten required classes have at least 300 originals each; Normal Machinery has 300, and Background Noise has 47 more than its base allocation. The raw and built audio live separately from the public source checkout because they take much more storage and carry source-specific license conditions. The repository holds per-clip metadata: class, source, source identifier, license, hashes, split group, and related quality information. Generated augmented windows are tracked separately and are not counted as new original recordings.

Sources include ESC-50, UrbanSound8K, FSD50K, MIMII valve recordings, RAVDESS, Nonspeech7k, and selected Freesound clips. Label maps translate their original labels into the project registry. A source name alone does not grant permission to redistribute every recording: the team records each clip's license and only published a small CC0 sample set in this repository. Freesound was particularly useful for filling Vehicle Horn, but text tags required listening and filtering; apparent horn matches could be imitations or unrelated alarms. The builder also rejects conflicting labels, silence, very short clips, and other unusable files. Its saved statistics report 41 rejections.

Person Asking for Help required a different route. The project records that no suitable public set was found, so the current 300 Help clips were generated as synthetic speech with varied voices and phrases under the documented permission. Related clips from one voice stay in the same split. That prevents the straightforward leak of a speaker's voice between training and test, but it does not make synthetic test voices equivalent to spontaneous human calls. Any future volunteer recordings need informed consent, clear retention rules, and careful handling of identifiable speech. The Help recording guide describes that process.

Split leakage was a central challenge. Multiple crops of one recording, two copies from different catalogs, or speech from one actor could otherwise appear in both training and test data. The builder uses hashes, source IDs, parent IDs, and group-aware splitting to hold related material together. Another challenge was source bias: some classes came mainly from one dataset, making microphone characteristics or factory ambience predictive of the label. A shortcut check found that raw recording-format features alone predicted class far above chance. Resampling, channel conversion, level normalization, trimming, and augmentation reduced those cues, but did not erase every environmental correlation. The dataset guide and preprocessing evidence describe the checks.

Audio preprocessing and feature extraction

Training and inference share a waveform pipeline so their inputs have the same meaning. Audio is converted to mono and 16 kHz, DC offset is removed, silence is trimmed, level is normalized, and the signal is divided into one-second windows with a half-second hop. Inference preserves the windows' order and timestamps so a clip result can point back to the relevant moment. Quality is assessed on the raw input before standardization; otherwise normalization could hide that a recording was originally weak or clipped. Noise reduction is available but disabled by default because it can erase short transients or damage the Background Noise category.

Augmentation acts on training material only. It mixes background noise, shifts time or pitch, changes gain and playback speed, adds reverberation, and simulates distance or microphone bandwidth. The augmented row retains its original Audio ID and training split. The purpose is to expose a model to plausible variations without allowing transformations of validation or test recordings to seep into training. Augmentation cannot manufacture a missing kind of real-world scene, so its results must still be checked against held-out source recordings.

For the classical models, the feature extractor calculates 123 summary values from MFCCs and deltas, chroma, mel bands, zero-crossing rate, RMS energy, spectral centroid, bandwidth, roll-off, contrast, flatness, and onset strength. It also creates a 64-by-63 log-mel spectrogram for the CNN. A log-mel image summarizes energy by time and perceptually spaced frequency band; it is a useful model input, while the page's display spectrogram helps a reviewer inspect a recording. The project omits tempo because a one-second sound window rarely supports a reliable beat estimate. The feature guide connects each computed field to its implementation.

Python model development and GTM training

The Python evaluation compares an RBF SVM and XGBoost using summary features, a CNN using log-mel arrays, and a YAMNet transfer model using frozen pretrained embeddings. A calibrated soft-voting ensemble combines the CNN and YAMNet probabilities. Candidate settings were tuned on validation data, then the held-out test split was used for final evaluation. The selected version is ensemble-20260928-1. Selection considered critical-class recall first, followed by validation macro F1, average critical recall, and speed. No candidate cleared every 85% critical-recall target, which is why the published results include an explicit missed target rather than a claim of full SRS compliance.

GTM followed a separate workflow. The project exported one-second training samples from the common training recordings and played them through a virtual audio input while Teachable Machine recorded. The documented run used roughly 143–145 samples per class, ten labels, 50 epochs, and batch size 16. Its TensorFlow.js export is stored in gtm_model/ and scored in the browser. A captured Alarm or Siren class had to be re-recorded after a training problem. Most importantly, this saved GTM export predates the Help-class extension: it has ten labels and does not include Person Asking for Help. The Python model and GTM are therefore independent, but their saved versions are not yet a matched 11-class pair.

The two paths are intentionally compared on labels and confidence after inference. GTM is a second opinion, not a training signal for Python and not a vote with equal authority in the final class. This design follows the earlier common-test result, where Python was substantially stronger. The web application records both raw class-score maps so a reviewer can revisit the decision after a human correction. See the model guide, GTM procedure, and saved model selection.

Models compared, confidence, and what the numbers mean

On the current 11-class Python test split, the selected ensemble reached 87.6% accuracy, 0.877 macro F1, 0.879 macro precision, and 0.879 macro recall. Macro F1 gives each class similar weight even when counts differ. It matters here because a rare critical sound should not vanish behind strong performance on an easier class. The measured 30-second upload model timing was 787 ms after model loading, on the evaluation setup; it is not a guarantee for every machine or concurrent production load.

The earlier Python-versus-GTM common test must be kept separate. It used the older ten-class Python ensemble and 450 unseen recordings. Python reached 86.4% accuracy, GTM 55.5%, and the application decision 85.3%. One GTM result was unavailable, so agreement summaries cover 449 scored pairs. The models chose the same class on 262; among 187 disagreements, Python was right on 150, GTM on 11, and neither on 26. Those counts explain why model agreement is useful context but cannot establish that a matching prediction is automatically correct.

The application stores each model's top confidence, top-two margin, full class scores, agreement state, and absolute difference between their top confidences. The older common test's mean confidence difference was 34.4 percentage points. A shared label with widely different confidence can be treated as a weak match; a high score on poor-quality audio also deserves caution. Confidence is a model estimate, not a probability that an emergency is truly occurring. The current Python evaluation and older dual-model comparison provide the underlying numbers and version identities.

Waveforms, spectrograms, and reviewable results

A predicted label by itself is too thin for sound investigation. The event page displays the audio player, source filename, duration, sample rate, quality grade, a waveform, and a spectrogram. The waveform shows amplitude over time, helping a reviewer locate a brief event and see whether a clip is quiet, clipped, or mostly silence. A spectrogram shows how frequency energy changes through time, helping distinguish sustained tones, broadband impacts, or voiced sounds. Neither image proves a category; both provide context for listening and model scores.

The current 11-class confusion matrix supplies a different visual check: rows are actual classes and columns are predicted classes. Its off-diagonal cells expose which sounds the classifier confuses. For example, strong aggregate accuracy can coexist with lower Aggression recall. A reviewer can inspect the figure below and compare it with the validation matrix. The matrices, per-class metrics, and robustness chart are saved in the repository rather than hidden behind a single headline score.

Alert rules and real-time monitoring

The decision engine begins with the Python top class, then considers audio quality, unknown and low-confidence thresholds, top-two margin, overlap, repeated detections, and model agreement. Defaults include a 0.50 minimum confidence, 0.10 top-two margin, 0.25 overlap threshold, and 0.35 Unknown threshold. Category rules add severity and action. A possible gunshot is Critical and requires two detections; Glass Breaking is High; Panic Scream and Person Asking for Help are Critical. Aggression is High and can escalate under stronger repeated evidence. These are configured rules, not an assurance that every detection is real.

When a rule fails, the event can be recorded as unconfirmed or sent for manual review rather than silently discarded. Authorized security and maintenance operators can acknowledge, dismiss, resolve, or escalate alerts; reviewers can correct a class while original model outputs remain stored. The audit trail matters because the person handling a sound should be able to see what the model said, what was changed, and why. Administrators can edit thresholds and rules, so a deployment must validate them against its actual setting instead of assuming competition defaults apply everywhere.

Live monitoring starts only when a user presses Start and grants microphone permission. The page shows capture state, current class, both model results, agreement, waveform, spectrogram, and any active alert. Pause and Stop controls let the user end capture visibly. Short prediction windows help identify a new event without waiting for a whole long recording. Browser permissions, microphone hardware, network latency, and backend inference all affect responsiveness; the saved offline timing numbers do not certify a live service-level target.

Difficulties, false positives, false negatives, and noise

A major early false-positive path was the factory shortcut. When Machinery Fault examples came from MIMII recordings, an early model could learn the sound of that recording environment rather than the fault. Adding Normal Machinery examples and retraining made the selected ensemble call 0 of 60 unseen normal-operation MIMII recordings Machinery Fault in the saved shortcut test. The SVM still called 23% faulty and YAMNet 48%. This is encouraging for that specific test, yet it does not prove zero false alarms in another factory, microphone position, or machine type. The episode taught us to test the background as well as the intended sound.

False negatives are more consequential for critical categories. In the current Python test, Glass Breaking recall is 91%, Gunshot 93%, Panic Scream 89%, and Aggression only 80%, below the SRS target of 85%. Roughly one in five saved Aggression test clips was not labeled Aggression. Help recall is 100% in this test, but every Help clip is synthetic; that score cannot be generalized to spontaneous speech in stress, accents, distance, and reverberation. A low-confidence or unavailable model output needs a clear review route, but review cannot recover a real event that was never captured or surfaced.

Model disagreement also has diagnostic value. In the earlier matched comparison, disagreement frequently favored Python, but in 11 cases GTM alone was right and in 26 neither model was right. A reviewer should therefore see the scores and hear the clip, not accept either model's identity by authority. The app records confidence difference and class-score maps so such disagreements can be inspected. A future matched 11-class comparison is necessary before claiming that the present Python ensemble and GTM export have a measured joint result.

Noise robustness was tested with simulated perturbations of held-out audio. The selected Python ensemble's macro F1 fell from 0.877 clean to 0.840 at 20 dB added noise, 0.735 at 5 dB, and 0.624 at 0 dB, where noise is as loud as the event. Quiet audio over microphone hiss fell to 0.492; simulated phone-band audio with clipping scored 0.803. The robustness chart shows the full comparison. These perturbations expose weaknesses and guide data collection, but they are not a substitute for a prospective test with real microphones and busy scenes.

Security and privacy in the implementation

Django authentication and role capabilities restrict who can inspect, review, export, configure, and handle events. CSRF and session middleware are enabled. Audio uploads are stored outside the public static directory and served through permission-checked views. Production mode requires a secret key and enables secure-cookie settings; the repository's .env.example contains no real credential. Event and action records support an audit trail. These are implemented controls, not evidence of a completed penetration test or hardened production deployment.

Audio may reveal identity, location, speech, or sensitive incidents even when the classifier only needs a category. The browser asks for microphone permission, capture begins through an explicit control, and the interface displays state. Uploaded audio is access-controlled; retention is configurable so stored records and files can be removed. Dataset metadata records origin and license, and the public sample set is deliberately limited to clips marked CC0. A real deployment would still need a documented lawful collection basis, consent where applicable, retention schedule, access review, and policies for human escalation.

Limitations, lessons learned, and future enhancements

The largest technical gap is version alignment: the saved GTM model has ten labels while the current Python ensemble has 11. GTM's older ten-class accuracy was below the SRS target, and the current Python ensemble misses the Aggression critical-recall target. Synthetic Help speech, source-concentrated classes, simulated noise tests, and unknown microphone environments limit generalization. The repository does not demonstrate the SRS's 20,000-record capacity, 99% availability, or concurrent-user targets. It also does not contain the full raw audio dataset, so reproducing training requires source downloads and license-aware rebuilding.

Several practical lessons came from the work. First, exact source identifiers and group-aware splits are as important as the model architecture because leakage can make test scores look better than reality. Second, an optional negative class such as Normal Machinery can fix a real operational failure mode that headline accuracy misses. Third, confidence, quality, and disagreement should be shown beside the label, not hidden in logs. Fourth, rules need a human-handling trail: a review queue and preserved original scores are part of the technical result. Finally, separate model versions and experiments must be labeled precisely; an older ten-class cross-model number cannot be combined with a newer 11-class Python score.

The next model iteration should collect consenting real Help voices and more varied Aggression scenes, then retrain GTM with the same 11 labels and common training split as Python. Both models should be re-evaluated on the same unseen recordings with per-class recall, calibration, agreement, and noise analysis. Thresholds should be retuned on validation data after each change. For product readiness, the team would also need measured concurrent-user and 20,000-record tests, uptime evidence, deployment documentation, and an operational review of privacy and response procedures. Until then, SonicSentinel remains a transparent prototype whose strongest result is the ability to show what it detected, why it alerted, and where the evidence is weak.
